# Как работает авторизация

## Краткая суть

В проекте параллельно живут **два механизма** аутентификации:

1. **Cookie-сессия** — для HTML-страниц. Подписанная cookie с одним полем `user_id`. Старлетка управляет ею через `SessionMiddleware`.
2. **JWT-токен** — для `/api/v1/*`. Stateless: сам токен содержит `sub=user_id` и подписан тем же `SECRET_KEY`. Живёт 7 дней.

Пароли — **bcrypt**, с прозрачной миграцией старых plaintext-аккаунтов. Email-верификация и сброс пароля сделаны через одноразовые **подписанные ссылки** (`itsdangerous`).

## Карта потоков

```
HTML-юзер                                  API-юзер
   │                                          │
   ▼                                          ▼
  POST /  (email + password)        POST /api/v1/auth/token  (form-data)
   │                                          │
   ▼                                          ▼
  verify_password() — bcrypt + legacy fallback (одинаково для обоих)
   │                                          │
   ▼                                          ▼
  login_session(user)                  encode_access_token(user.id)
  request.session["user_id"] = user.id          │
   │                                          ▼
   ▼                                  возвращаем JWT в JSON
  RedirectResponse(/main)
```

И в обоих случаях — следующий запрос:

```
HTML:    cookie → get_current_user_optional → user или RedirectToLogin
API:     Authorization: Bearer ... → decode_access_token → user или 401
         (если Bearer'а нет → fallback на cookie)
```

## Где лежит сессия и как она работает

[app/main.py:21](../app/main.py#L21):

```python
app.add_middleware(SessionMiddleware, secret_key=SECRET_KEY, max_age=60 * 60 * 24 * 30)
```

Это middleware из Starlette: оно прозрачно сериализует словарь `request.session` в JSON, подписывает его HMAC'ом по `SECRET_KEY` и отправляет браузеру в cookie. На вход — наоборот: парсит cookie и проверяет подпись. Если подпись битая — игнорирует.

В этой сессии мы храним всего одну вещь — `user_id`:

[app/deps.py:66-71](../app/deps.py#L66-L71):

```python
def login_session(request: Request, user: User) -> None:
    request.session["user_id"] = user.id

def logout_session(request: Request) -> None:
    request.session.pop("user_id", None)
```

**Важно**: cookie у нас не «помнящая всё про юзера», а просто «помнящая ID». Все остальные поля (имя, права, email) каждый раз достаются из БД по этому ID. Это значит, что если юзера удалить — следующий же запрос увидит `None` и попросит залогиниться.

## Получение «текущего юзера»

Файл [app/deps.py](../app/deps.py) — три функции, плотно нагруженные DI:

### `get_current_user_optional` ([app/deps.py:22-32](../app/deps.py#L22-L32))

Безопасный «может быть юзер, может нет». Используется на главной странице (если зашёл — редирект на `/main`, если нет — показываем форму входа).

```python
user_id = request.session.get("user_id")
if user_id is None:
    return None
user = await crud.get_user_by_id(db, int(user_id))
if user is None:
    request.session.pop("user_id", None)  # юзера удалили — чистим cookie
return user
```

### `get_current_user` ([app/deps.py:35-42](../app/deps.py#L35-L42))

Жёсткое «или юзер, или вон». Используется во всех HTML-роутах, требующих логина.

```python
user = await get_current_user_optional(request, db)
if user is None:
    raise RedirectToLogin()  # обработчик в main.py превратит в 303 на /
return user
```

### `get_current_user_api` ([app/deps.py:45-63](../app/deps.py#L45-L63))

Хитрая версия для `/api/v1/*` с **двумя источниками**:

```python
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/token", auto_error=False)

async def get_current_user_api(token: Optional[str] = Depends(oauth2_scheme), ...):
    if token is not None:
        user_id = decode_access_token(token)         # JWT в Authorization
        ...
    user = await get_current_user_optional(request, db)  # fallback на cookie
    if user is None:
        raise HTTPException(status_code=401, ...)
    return user
```

**Зачем оба**:

- JWT — для внешних клиентов (мобилка, скрипты). Они получают токен на `/api/v1/auth/token` и потом везде шлют `Authorization: Bearer ...`.
- Cookie — чтобы Swagger UI (`/docs`) и сам Jinja-юзер тоже могли тыкать API без отдельного логина.

`auto_error=False` ([app/deps.py:15](../app/deps.py#L15)) — если заголовка нет, FastAPI не падает с 401, а отдаёт `None`. Это и позволяет нам сделать fallback.

## Хеширование паролей: `app/security.py`

Минимальный модуль, всего ~20 строк, но за ним важная мысль.

[app/security.py:1-3](../app/security.py#L1-L3):

```python
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
```

`CryptContext` — это «менеджер схем хеширования» из passlib. Сейчас разрешён только bcrypt, но если завтра захочется добавить argon2 — достаточно вписать его в список, и старые bcrypt-хеши останутся валидными.

### Распознавание формата ([app/security.py:10-11](../app/security.py#L10-L11))

```python
def is_hashed(password: str) -> bool:
    return password.startswith("$2a$") or password.startswith("$2b$") or password.startswith("$2y$")
```

Bcrypt-хеши **всегда** начинаются на один из этих префиксов. Если строка их не содержит — это plaintext, унаследованный из «древних» аккаунтов.

### Verification + миграция ([app/security.py:14-21](../app/security.py#L14-L21))

```python
def verify_password(plain: str, stored: str) -> bool:
    if is_hashed(stored):
        try:
            return pwd_context.verify(plain, stored)
        except Exception:
            return False
    return plain == stored  # legacy
```

Главный приём — **прозрачная миграция при логине**. В роуте логина ([app/routers/auth.py:68-69](../app/routers/auth.py#L68-L69)):

```python
if not is_hashed(user.password):
    await crud.update_user_password(db, user.id, hash_password(password))
```

Юзер заходит со старым plaintext-паролем — проверяем `plain == stored`, дальше сразу же сохраняем правильный bcrypt-хеш. На следующем логине этот же пароль уже пойдёт по основной ветке `pwd_context.verify`. Plaintext в базе исчезнет естественным путём, без миграции на стороне БД.

## Регистрация и подтверждение email

### Регистрация ([app/routers/auth.py:88-115](../app/routers/auth.py#L88-L115))

```python
@router.post("/registration")
async def register_page_post(...):

```

Юзер сразу залогинивается (можно пользоваться сайтом), но `confirmed=False`.

### Письмо подтверждения

В `app/email.py` есть `send_verification_email`, который генерирует одноразовую ссылку через `make_verify_token` и кладёт в письмо.

Токены живут в [app/tokens.py](../app/tokens.py):

```python
VERIFY_SALT = "email-verify-v1"

def _s(salt: str) -> URLSafeTimedSerializer:
    return URLSafeTimedSerializer(SECRET_KEY, salt=salt)

def make_verify_token(email: str) -> str:
    return _s(VERIFY_SALT).dumps(email)

def read_verify_token(token: str) -> str:
    return _s(VERIFY_SALT).loads(token, max_age=VERIFY_TOKEN_TTL)
```

Это **подписанные одноразовые ссылки** через `itsdangerous`:

- Внутри токена лежит сам email + timestamp + подпись.
- Подпись делается тем же `SECRET_KEY` (плюс уникальный `salt`, чтобы verify-токен нельзя было использовать как reset-токен).
- При проверке `loads(...)` сверяет подпись и проверяет возраст. Если старше `max_age` — `SignatureExpired`.

### Обработчик клика ([app/routers/auth.py:118-156](../app/routers/auth.py#L118-L156))

```python
@router.get("/verify-email/{token}")
async def verify_email(...):
    try:
        email = read_verify_token(token)
    except TokenError:
        ...    # 400, ссылка устарела/битая
    user = await crud.get_user_by_email(db, email)
    ...
    if not user.confirmed:
        await crud.mark_user_confirmed(db, user.id)
    ...
```

Хороший паттерн — токен сам по себе и есть «параметр запроса». Никакой записи в БД про токен не нужно: мы доверяем подписи.

## Сброс пароля

Аналогично подтверждению, только другой `salt` и TTL короче (1 час вместо 3 дней).

[app/routers/auth.py:175-192](../app/routers/auth.py#L175-L192) — запрос на сброс:

```python
@router.post("/password-reset")
async def password_reset_request_post(...):
    user = await crud.get_user_by_email(db, email)
    if user is not None:
        _send_password_reset_email(user)
    # intentionally no leak whether user exists
    return ...
```

**Важная деталь**: ответ одинаковый и для существующего, и для несуществующего email. Это защита от **user-enumeration**: злоумышленник не может перебором по форме найти, какие email зарегистрированы.

[app/routers/auth.py:232-288](../app/routers/auth.py#L232-L288) — установка нового пароля:

- Проверяем токен (1 час TTL).
- Проверяем `password == password2` и `len(password) >= 6`.
- `crud.update_user_password(...)` записывает новый bcrypt-хеш.
- `logout_session(request)` — сбрасываем все активные сессии (если кто-то украл cookie, она перестанет работать).

## JWT для API: `app/jwt_auth.py`

Совсем коротко:

[app/jwt_auth.py:12-13](../app/jwt_auth.py#L12-L13):

```python
ALGORITHM = "HS256"
ACCESS_TOKEN_TTL = 60 * 60 * 24 * 7  # 7 дней
```

[app/jwt_auth.py:16-19](../app/jwt_auth.py#L16-L19):

```python
def encode_access_token(user_id: int) -> str:
    now = int(time.time())
    payload = {"sub": str(user_id), "iat": now, "exp": now + ACCESS_TOKEN_TTL}
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)
```

Токен возвращается из `/api/v1/auth/token` ([app/routers/api/auth.py:73-87](../app/routers/api/auth.py#L73-L87)) после OAuth2 password flow. Дальше клиент кладёт его в `Authorization: Bearer <token>`, и `decode_access_token` извлекает `user_id`.

Поскольку токен подписан тем же `SECRET_KEY`, что и cookie-сессии, у нас одна точка отзыва: меняем `SECRET_KEY` — все cookie и все JWT мгновенно становятся невалидными.

## Различие реакции HTML vs API

| | HTML-роуты | `/api/v1/*` |
|---|---|---|
| Зависимость | `get_current_user` | `get_current_user_api` |
| Источник | cookie | Bearer-токен → cookie (fallback) |
| Нет авторизации | `RedirectToLogin` → 303 на `/` | `HTTPException(401)` JSON |
| Формат входа | `Form(...)` (multipart) | JSON (`pydantic.BaseModel`) |
| Что выставляется | cookie | возвращается JWT в JSON |

Это сделано осознанно: API не должно отдавать редирект (внешнему клиенту это бесполезно), а браузеру — JSON 401 (он не знает, что с ним делать).

## Двойной выход

- HTML: `GET /logout` → `logout_session(request)` → 303 на `/` ([app/routers/auth.py:75-78](../app/routers/auth.py#L75-L78)).
- API: `POST /api/v1/auth/logout` → требует `get_current_user_api` → чистит сессию → JSON `{message: "Выход выполнен"}` ([app/routers/api/auth.py:38-44](../app/routers/api/auth.py#L38-L44)).

JWT при «выходе» **не отзывается** — он stateless и продолжит работать до своего `exp`. Если нужно вырубить токен раньше времени, придётся либо хранить чёрный список, либо сменить `SECRET_KEY` (вырубит всех).

## Технологии под капотом

### Cookie-сессии (Starlette `SessionMiddleware`)
Старая, но рабочая модель: сервер пишет в cookie сериализованный словарь, подписывает его HMAC'ом. Браузер сам пересылает cookie на каждом запросе. Преимущества — простота и stateful (сервер знает, кто залогинен через смену `SECRET_KEY`). Недостатки — нужно беречь cookie от XSS (`HttpOnly`, `Secure`).

### JWT (JSON Web Token)
Stateless-токен, состоящий из трёх частей через точку: `header.payload.signature`. Внутри `payload` лежат claims (стандартные `sub`/`iat`/`exp` + любые свои). Подпись HMAC-SHA256 — для проверки. Плюсы: сервер не хранит сессии, легко масштабируется. Минусы: нельзя «отозвать» токен без стороннего хранилища.

### bcrypt
Хеш-функция, специально замедленная (cost factor задаёт число итераций). Включает соль внутри самого хеша, поэтому одинаковые пароли получают разные хеши. Нет смысла «поднимать сложность» — `passlib` сам обновляет cost при verify.

### itsdangerous
Микробиблиотека Pallets для **подписанных строк**. `URLSafeTimedSerializer` оборачивает любые JSON-сериализуемые данные в URL-безопасный токен с timestamp'ом — идеальный инструмент для одноразовых email-ссылок. Никакого шифрования: данные читаются, подделать нельзя.

### OAuth2 password flow
Один из «потоков» в стандарте OAuth2 — простейший: клиент шлёт `username` + `password` form-data, получает access-token. Реально это уже legacy (его не рекомендуют), но FastAPI его поддерживает «из коробки» через `OAuth2PasswordBearer` + `OAuth2PasswordRequestForm`, что удобно для Swagger UI с кнопкой «Authorize».
