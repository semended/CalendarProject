# Как работает диаграмма Ганта

## Краткая суть

Диаграмма Ганта — это страница «Таймлайн» внутри обзора задачи (`/task/{id}/overview`). Реализована **полностью на сервере**: Python в роуте считает позиции и ширины полос в **процентах**, а Jinja вставляет их прямо в `style="..."` элементов. CSS Grid раскладывает строки.

Никаких JS-библиотек (D3, Chart.js, frappe-gantt) нет — всё своё. Интерактивности тоже минимум: hover на полосе и клик на вкладку «Дерево» / «Таймлайн».

## Где это всё живёт

| Слой | Файл | Что делает |
|---|---|---|
| Роут (расчёт) | [app/routers/tasks.py:223-351](../app/routers/tasks.py#L223-L351) | Собирает дерево, считает `pct(dt)`, делает `rows` |
| Шаблон (HTML) | [templates/task_overview.html:35-87](../templates/task_overview.html#L35-L87) | Рисует grid через CSS-переменные |
| Стили | [static/css/style.css](../static/css/style.css) | CSS Grid, цвета полос, hover (секция Gantt) |

## Шаг 1 — собираем дерево подзадач

[app/routers/tasks.py:233-240](../app/routers/tasks.py#L233-L240):

```python
async def collect_descendants(node: Task):
    children = await crud.get_subtasks(db, node.id)
    out = []
    for c in children:
        out.append({"task": c, "children": await collect_descendants(c)})
    return out

tree = await collect_descendants(root) if root else []
```

Это рекурсивный обход — для каждой подзадачи рекурсивно собираются её подзадачи. Результат — вложенный список словарей.

## Шаг 2 — превращаем дерево в плоский список «строк»

[app/routers/tasks.py:252-261](../app/routers/tasks.py#L252-L261):

```python
rows_raw = []  # (task, depth, track_id)

def walk_tree(nodes, depth=0, track_id=None):
    for idx, n in enumerate(nodes):
        local_track = track_id if track_id is not None else idx
        rows_raw.append((n["task"], depth, local_track))
        walk_tree(n["children"], depth + 1, local_track)

walk_tree(tree)
```

Каждая строка получает три атрибута:

- **task** — сама задача;
- **depth** — глубина (0, 1, 2, ...). Используется для отступа влево;
- **track_id** — ID «трека»: подзадача первого уровня и все её потомки получают одинаковый `track_id`. Это позволяет красить «цепочки» одним цветом.

## Шаг 3 — выбираем диапазон дат

[app/routers/tasks.py:263-277](../app/routers/tasks.py#L263-L277):

```python
now = datetime.now()
starts = [root.created_at] if root and root.created_at else []
ends = []
for t, _, _ in rows_raw:
    if t.created_at: starts.append(t.created_at)
    if t.ended_at:   ends.append(t.ended_at)

start = min(starts) if starts else now
fallback_end = start + timedelta(days=30)
end = max(ends) if ends else fallback_end
if end <= start:
    end = start + timedelta(days=30)
```

Логика:

- Левая граница диаграммы = самая ранняя `created_at` среди всех задач (включая корневую).
- Правая граница = самая поздняя `ended_at`. Если дедлайнов нет вообще — берём «start + 30 дней» как fallback.
- Если по какой-то причине `end <= start` — снова +30 дней. Без этого диаграмма схлопнется в нулевую ширину.

## Шаг 4 — формула `pct(dt)`

Сердце диаграммы ([app/routers/tasks.py:279-280](../app/routers/tasks.py#L279-L280)):

```python
def pct(dt: datetime) -> float:
    return max(0.0, min(100.0, (dt - start).total_seconds() / total_seconds * 100.0))
```

Линейная интерполяция: дата → процент от диапазона `[start, end]`. С `clamp(0, 100)` на случай, если задача залезет за края.

Дальше для каждой задачи ([app/routers/tasks.py:295-318](../app/routers/tasks.py#L295-L318)):

```python
left = pct(t_start)
width = max(1.5, pct(t_end) - left)
```

`max(1.5, ...)` — чтобы очень короткая задача не превратилась в невидимую палочку нулевой ширины.

## Шаг 5 — окраска полос

```python
if t.state == "done":
    cls = "done"
elif t.ended_at and t.ended_at < now:
    cls = "overdue"
else:
    cls = "open"
```

Три класса CSS:

- `.bar.done` — выполненная (бледный, светлый);
- `.bar.overdue` — просроченная (красная);
- `.bar.open` — в работе (цвет трека).

## Шаг 6 — палитра треков

[app/routers/tasks.py:285-293](../app/routers/tasks.py#L285-L293):

```python
TRACK_PALETTE = [
    "#b84a28", "#5a7a4a", "#7c4a6b", "#a67f2a",
    "#2f6b89", "#9c4c2c", "#4f6d8c", "#7a5a2c",
]
for i, n in enumerate(first_level):
    own = (n["task"].color or "").lower()
    root_color = (root.color or "").lower() if root else ""
    if own and own != root_color:
        track_color_by_id[i] = n["task"].color   # юзер задал цвет → берём его

```

Логика «или явный цвет от пользователя, или из палитры по индексу» нужна потому, что в текущем демо все подзадачи наследуют цвет корня — без палитры все треки слились бы в один блоб.

## Шаг 7 — линия «сегодня» и axis ticks

[app/routers/tasks.py:320-325](../app/routers/tasks.py#L320-L325):

```python
today_pct = round(pct(now), 2) if start <= now <= end else None

axis_ticks = []
for i in range(6):
    tick_dt = start + timedelta(seconds=total_seconds * i / 6)
    axis_ticks.append(tick_dt.strftime("%d.%m"))
```

6 равномерных меток сверху и одна вертикальная линия для текущего момента (если он попадает в диапазон).

## Шаг 8 — рендер в шаблоне

[templates/task_overview.html:53-77](../templates/task_overview.html#L53-L77):

```html
<div class="gantt-grid" style="--cols: {{ axis_ticks|length }};">
    <div class="gantt-corner"></div>
    <div class="gantt-axis">
        {% for tick in axis_ticks %}
        <div class="tick tabular">{{ tick }}</div>
        {% endfor %}
    </div>

    {% for r in rows %}
    <div class="gantt-label ..." title="{{ r.task.name }}">
        <span class="dot" style="background: {{ r.color }};"></span>
        <span class="name" style="padding-left: {{ r.depth * 12 }}px;">{{ r.task.name }}</span>
    </div>
    <div class="gantt-track ...">
        <div class="bar {{ r.cls }}"
             style="--left: {{ r.left }}%; --width: {{ r.width }}%; --bar-color: {{ r.color }};"
             ...></div>
        {% if loop.first and today_pct is not none %}
        <div class="gantt-today" style="left: {{ today_pct }}%;"></div>
        {% endif %}
    </div>
    {% endfor %}
</div>
```

Грид `gantt-grid` имеет две колонки: «название» (`gantt-label`) + «полоса» (`gantt-track`), а каждая строка задачи добавляет два таких блока подряд. CSS Grid сам выстроит их в табличку.

CSS-переменные `--left` / `--width` / `--bar-color` берутся из inline-style и используются в `static/css/style.css`:

```css
.bar {
    position: absolute;
    left: var(--left);
    width: var(--width);
    background: var(--bar-color);
}
```

То есть **вся вёрстка диаграммы — это просто `position: absolute` + проценты**. Переменные CSS — удобный способ протащить параметры из шаблона в стили без раздутия inline-styles.

## Что НЕ реализовано (важно знать)

- **Нет drag-and-drop**. Двигать полосы мышкой нельзя. Если захочешь добавить — это уже JS-уровень: слушаем `mousedown` → `mousemove`, считаем дельту в пикселях → конвертим в дельту дат через ту же `pct`-формулу наоборот → шлём PATCH в `/api/v1/tasks/{id}`.
- **Нет клика по полосе**. Клик ничего не делает (хотя `cursor: pointer` стоит — наследие). Чтобы сделать переход — оборачиваем `<div class="bar">` в `<a href="/task/{{ r.task.id }}">`.
- **Нет стрелок зависимостей**. Их в модели данных просто не существует: между задачами есть только `parent_task_id`, а понятия «эта задача блокирует ту» нет. Чтобы добавить — нужна новая таблица типа `task_dependencies(from_id, to_id)` и SVG-линии в шаблоне.
- **Нет виртуализации**. Если задач 5000 — браузер будет рендерить 5000 DOM-элементов и подтормаживать. На текущих масштабах (учебный проект) это не проблема.
- **Не масштабируется по zoom'у**. Диаграмма всегда занимает ровно ширину контейнера — увеличить «миллисекундное разрешение» нельзя.

## Технологии под капотом

### CSS Grid
Двумерная система раскладки в CSS. Главные свойства:

- `display: grid` + `grid-template-columns: ...` задают сетку;
- `grid-column: 1 / 3` — занять колонки 1–2;
- автогенерация строк при добавлении дочерних элементов.

В нашем случае грид «авто-табличный»: пары `(label, track)` сами выстраиваются в строки.

### CSS-переменные (custom properties)
Объявляются как `--name: value` (например, в inline `style="--left: 32%;"`), читаются как `var(--name)` в CSS. Удобны для протаскивания «динамических» значений из шаблона в стили без генерации уникальных классов.

### Jinja2 inline-styles
В обычной фронтенд-разработке inline-styles считаются плохим тоном (нельзя кешировать, мешают reuse). Но для серверного Ганта это идеально: значения уникальны для каждой задачи, кэшировать всё равно нечего, а альтернатива — генерить уникальный CSS для каждой страницы — была бы сложнее.
