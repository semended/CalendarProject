# Как устроена система проектов

## Краткая суть

В CalendarProject **нет отдельной таблицы `projects`**. «Проект» — это просто `Task` без родителя (`parent_task_id IS NULL`). Подзадачи — те же Task, но с `parent_task_id`, указывающим вверх по дереву. То есть «проект» и «задача» — это одна сущность, отличающаяся только местом в иерархии.

Поверх этого построен **RBAC** (role-based access control) на трёх таблицах: для каждой задачи существуют свои роли (Тимлид/Менеджер/Разработчик), у каждой роли — свой набор прав, а пользователь получает права через назначение в ролях. Права **наследуются вверх по дереву**: если у юзера нет роли в подзадаче — система проверит его роль в родителе, и так до корня.

## Главная идея в одной картинке

```
            ┌───────────────────────────────┐
            │ Task #1 — «Сайт» (root)       │   parent_task_id = NULL
            │ creator: Вова                 │   ← это «проект»
            │ TaskRoles: Тимлид, Менеджер,  │
            │            Разработчик        │
            │ TaskUserRole: Вова → Тимлид   │
            └───┬───────────────────────────┘
                │
        ┌───────┴───────┐
        │               │
┌───────▼─────┐  ┌──────▼──────┐
│ Task #2     │  │ Task #3     │   parent_task_id = 1
│ «Backend»   │  │ «Frontend»  │   у этих тасок свои Тимлид/Менеджер/Разраб
└───┬─────────┘  └─────────────┘   (создаются автоматически)
    │
┌───▼──────┐
│ Task #4  │   parent_task_id = 2
│ «Auth»   │
└──────────┘
```

И теперь главное: если **пользователь Петя** добавлен Менеджером в `Task #1` (root) — он автоматически имеет права Менеджера и в #2, #3, #4 (через наследование). Если он добавлен Разработчиком только в #2 — в #1 и #3 у него **никаких прав нет**.

## Модель: одна таблица для всего

[app/models.py:42-76](../app/models.py#L42-L76):

```python
class Task(Base):
    __tablename__ = "tasks"

    id             = Column(BigInteger, primary_key=True)
    parent_task_id = Column(BigInteger, ForeignKey("tasks.id", ondelete="CASCADE"), nullable=True)
    creator_id     = Column(BigInteger, ForeignKey("users.id"))
    assignee_id    = Column(BigInteger, ForeignKey("users.id"), nullable=True)
    name           = Column(String(255))
    description    = Column(Text)
    color          = Column(Text)
    duration       = Column(BigInteger)
    state          = Column(String(20), server_default="todo")     # todo|in_progress|review|done|paused
    created_at     = Column(DateTime, server_default=func.now())
    ended_at       = Column(DateTime, nullable=True)               # дедлайн

    parent_task = relationship("Task", remote_side=[id], back_populates="subtasks")
    subtasks    = relationship("Task", back_populates="parent_task")
```

Self-referential FK (`parent_task_id` → `tasks.id`) — стандартный приём для деревьев в SQL. `ondelete="CASCADE"` означает, что при удалении родителя все потомки удалятся вместе с ним.

## Три таблицы прав

### `TaskRole` — роли в задаче

[app/models.py:100-112](../app/models.py#L100-L112):

```python
class TaskRole(Base):
    __tablename__ = "task_roles"
    id      = Column(BigInteger, primary_key=True)
    task_id = Column(BigInteger, ForeignKey("tasks.id", ondelete="CASCADE"))
    name    = Column(String(255))   # "Тимлид" / "Менеджер" / "Разработчик"
```

Роли — **локальные для каждой задачи**, не глобальные. У каждого проекта будет свой `Тимлид (id=1)`, у соседнего — свой `Тимлид (id=10)`. Это позволяет, например, переименовать роли в одном проекте, не трогая другие.

### `TaskUserRole` — кто какую роль имеет

[app/models.py:129-150](../app/models.py#L129-L150):

```python
class TaskUserRole(Base):
    id            = Column(BigInteger, primary_key=True)
    user_id       = Column(BigInteger, ForeignKey("users.id", ondelete="CASCADE"))
    task_id       = Column(BigInteger, ForeignKey("tasks.id", ondelete="CASCADE"))
    task_role_id  = Column(BigInteger, ForeignKey("task_roles.id", ondelete="CASCADE"))

    __table_args__ = (
        UniqueConstraint("user_id", "task_id", "task_role_id", ...),
        ...
    )
```

Это «join table» три-в-одном. UNIQUE-ограничение на тройку гарантирует, что юзер не получит одну и ту же роль дважды. Один юзер, впрочем, может иметь **несколько разных ролей** в одной задаче (например, и Тимлид, и Разработчик).

- **Разработчик** — смотреть и создавать подзадачи.

## Как создаётся «проект»

Поток создания корневой задачи:

1. Пользователь жмёт «Новый проект» на `/main` → попадает в форму `/create_task` ([app/routers/tasks.py:94-100](../app/routers/tasks.py#L94-L100)).
2. POST формы вызывает `crud.create_task_bundle` (или `crud.create_task` для подзадач).
3. **Бандл** делает в одной транзакции четыре вещи ([app/crud.py:129-151](../app/crud.py#L129-L151)):

```python
async def create_task_bundle(db, creator_id, name, description, color, duration, ...):
    task = await create_task(db, creator_id, name, description, ...)   # 1. сама Task
    teamlead = await create_task_role(db, task.id, "Тимлид")            # 2. три TaskRole
    manager  = await create_task_role(db, task.id, "Менеджер")
    dev      = await create_task_role(db, task.id, "Разработчик")
    for role in (teamlead, manager, dev):
        await ensure_role_permissions(db, role)                         # 3. навесить права
    await assign_user_to_task_role(db, creator_id, task.id, teamlead.id)  # 4. создатель = Тимлид
    return task
```

В итоге после `create_task_bundle` создатель сразу имеет полный контроль, а у задачи готова инфраструктура для добавления других участников.

`ensure_role_permissions` ([app/permissions.py:30-39](../app/permissions.py#L30-L39)) — идемпотентная функция: если у роли уже есть права, ничего не делает; иначе создаёт строки из `ROLE_DEFAULTS`.

## Добавление участника

[app/routers/tasks.py:393-433](../app/routers/tasks.py#L393-L433) — POST `/task_management/{task_id}` принимает email + role_id и:

1. Проверяет у текущего юзера право `P_MANAGE_MEMBERS`.
2. Находит юзера по email.
3. Вызывает `crud.assign_user_to_task_role(db, user.id, task.id, role.id)` ([app/crud.py:305-312](../app/crud.py#L305-L312)).

Никакой инвайт-системы или подтверждения — добавление мгновенное. Это упрощённая модель для учебного проекта.

## Главное: наследование прав

Самый интересный кусок системы. Файл [app/permissions.py:54-66](../app/permissions.py#L54-L66):

```python
async def has_permission(db: AsyncSession, user_id: int, task_id: int, perm: str) -> bool:
    cur_id: Optional[int] = task_id
    while cur_id is not None:
        role = await _find_role_in_task(db, user_id, cur_id)
        if role is not None:
            await ensure_role_permissions(db, role)
            return any(p.permission == perm for p in role.permissions)
        task = await db.get(Task, cur_id)
        if task is None:
            break
        cur_id = task.parent_task_id      # ← поднимаемся вверх
    return False
```

Алгоритм:

1. Начинаем с текущей задачи `task_id`.
2. Если у юзера в **этой** задаче есть роль → проверяем, есть ли в ней право `perm`. Возвращаем результат.
3. Если роли нет — поднимаемся к `parent_task_id` и повторяем.
4. Дошли до корня (parent_task_id = NULL) и так и не нашли роль → у юзера **нет** прав. `False`.

**Интересный side-effect**: первая найденная вверх по дереву роль сразу решает «да/нет», даже если выше есть «более широкая» роль. То есть если ты Менеджер в подпроекте, но Тимлид в корне — для подпроекта будут действовать **только** права Менеджера. Это сознательный выбор: «локальная» роль перезаписывает «глобальную».

## Как используется на практике

Любой роут, требующий прав, вызывает `has_permission` в начале:

```python
# app/routers/api/tasks.py:113
if not await has_permission(db, user.id, task_id, P_EDIT_SETTINGS):
    raise HTTPException(status_code=403, detail="Нет прав на редактирование задачи")
```

Это единственное API проверки. Никаких миддлварей или декораторов — просто явный вызов.

Для удобства есть `user_perms` ([app/permissions.py:69-70](../app/permissions.py#L69-L70)): возвращает словарь `{permission: bool}` для всех прав сразу — пригодится в шаблоне, чтобы скрывать кнопки, на которые у юзера нет прав.

## Технологии под капотом

### Self-referential foreign key (иерархия в SQL)
Колонка `parent_task_id` ссылается на ту же таблицу `tasks(id)`. Базовый приём для деревьев и графов в реляционной БД. Альтернативы — closure tables, nested sets, materialized paths — нужны при больших объёмах (миллионы записей и частые запросы «все потомки»). Для нашего объёма обычная рекурсия по родителям работает отлично.

### RBAC (Role-Based Access Control)
Модель «пользователь → роль → права». Три уровня абстракции вместо двух (как было бы в ACL «пользователь → права»). Плюс — гибко: дать новому юзеру «такие же права как у Менеджера» — это одно действие, а не пять.

### Наследование прав вверх по дереву
Не самая распространённая модель — обычно RBAC «плоский». Но в иерархических доменах (файловая система, организационная структура, проекты) она очень удобна. Альтернатива — материализовать права в каждом узле (быстрее на чтение, дороже на запись).

### Functional CRUD-стиль
В этом проекте `crud.py` — это **набор функций**, а не класс с методами. Аргументы передаются явно (`db: AsyncSession`), state не хранится. Плюсы — легко тестировать, легко переиспользовать. Минус — много параметров в сигнатурах. На наших масштабах плюсы перевешивают.
