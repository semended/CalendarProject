# Этап 2: Стабильная двойная авторизация (cookie + JWT)

## Зачем

Сейчас в [app/deps.py](../app/deps.py) логика «JWT → fallback session» уже есть,
но она полу-документирована и не покрыта тестами на edge-cases. Нужно довести
её до production-качества: чтобы любой клиент (браузер, Swagger UI, мобилка,
curl-скрипт) аутентифицировался предсказуемо.

## Что нужно изучить

1. **OAuth2 Bearer vs cookies:** когда какой механизм уместен.
2. **CSRF в cookie-sessions:** почему API на cookies требует защиты от CSRF, а Bearer — нет.
3. **Refresh-токены:** когда они нужны и почему access-only TTL=7 дней — компромисс.

## Подэтапы

1. **Чёткое разделение namespace'ов:**
   - HTML-роуты (`/main`, `/task/...`) — **только cookie**. JWT в Authorization игнорируется.
   - API-роуты (`/api/v1/*`) — **JWT приоритет, cookie fallback** для Swagger UI.

2. **Эндпоинты JWT:**
   - `POST /api/v1/auth/token` — выдать JWT по логину+паролю (уже есть в `I`, проверить контракт).
   - `POST /api/v1/auth/refresh` — обновить access-токен (опционально, если решим вводить refresh).

3. **CSRF для HTML:**
   - Подключить `fastapi-csrf-protect` или ручной double-submit cookie pattern.
   - Все POST/PATCH/DELETE на HTML-роутах должны требовать CSRF-токен в форме.

4. **Тесты:**
   - JWT-доступ к API без cookie — работает.
   - Cookie-доступ к API из Swagger UI — работает.
   - JWT в HTML-роуте игнорируется (нельзя обойти CSRF через Bearer).
   - HTML POST без CSRF-токена → 403.

## Критерий завершения

- `tests/test_api_jwt.py` покрывает все 4 сценария выше.
- В `/docs` явно указано: «Authorize → Bearer».
- В CLAUDE.md обновлена секция «Gotchas» про CSRF.
