# Этап 3: Доделать модель данных

## Зачем

В [TODO.md](../TODO.md) явно: «Доделать бд (сейчас там только users и roles)».
Текущая схема покрывает MVP, но для production не хватает:
- историчности (когда задача меняла состояние, кто менял),
- комментариев и вложений к задачам,
- уведомлений (in-app + email),
- last_login на пользователе (нужно для security/аудита).

## Что нужно изучить

1. **Audit log pattern:** отдельная таблица событий vs триггеры в Postgres.
2. **Soft delete:** `deleted_at` vs физическое удаление (FK cascade).
3. **Alembic best practices:** не редактировать применённые миграции, использовать `op.execute()` для data-миграций.

## Подэтапы

1. **Добавить недостающие поля в `User`** (TODO.md п.5):
   - `last_login: DateTime | null`
   - убедиться что `position`, `company`, `workplace` уже есть (они есть — TODO устарел).
   - Миграция `xxxx_user_last_login.py`.

2. **Аудит изменений задач.** Новая таблица `task_events`:
   - `id`, `task_id`, `actor_id`, `event_type` (enum: created/state_changed/assignee_changed/...), `payload jsonb`, `created_at`.
   - Записываем из `services/task_service.py` (после Этапа 1).

3. **Комментарии к задачам.** `task_comments`:
   - `id`, `task_id`, `author_id`, `body text`, `created_at`, `edited_at | null`.

4. **Уведомления.** `notifications`:
   - `id`, `user_id`, `kind`, `payload jsonb`, `read_at | null`, `created_at`.
   - Триггерится из сервисов при назначении задачи, смене состояния, упоминании в комментарии.

5. **Soft delete для задач** (опционально, обсудить):
   - `tasks.deleted_at`. Все запросы фильтруют `deleted_at IS NULL`.

## Критерий завершения

- Все новые таблицы покрыты Alembic-миграциями.
- `db.sql` помечен как deprecated в начале файла (см. Этап 5).
- Сервисы создают `task_events` и `notifications` в нужных местах.
- Тесты в `tests/test_api_integration.py` проверяют, что событие пишется при смене state.
