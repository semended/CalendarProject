# Этап 1: Унификация слоёв SSR ↔ API

## Зачем

Главный риск гибрида — **расхождение логики** между HTML-роутерами и `/api/v1`.
Например, HTML может позволить создать задачу, а API — отказать (или наоборот).
Нужно гарантировать, что обе ветки идут через один и тот же бизнес-слой.

## Что нужно изучить

1. **Принцип Single Source of Truth для бизнес-логики.**
2. **Service layer pattern:** разделение «контроллер (роутер)» и «бизнес-логика».
3. **FastAPI `Depends`:** как пробрасывать общие зависимости в обе ветки.

## Подэтапы

1. **Аудит дубликатов.** Пройти по парам файлов:
   - `app/routers/auth.py` ↔ `app/routers/api/auth.py`
   - `app/routers/tasks.py` ↔ `app/routers/api/tasks.py`
   - `app/routers/users.py` ↔ `app/routers/api/users.py`

   Для каждой пары выписать: где есть логика, которой нет в `crud.py`/`permissions.py`.

2. **Вынести расхождения в `app/services/`** (новая папка):
   - `services/auth_service.py` — `register_user`, `authenticate_user`
   - `services/task_service.py` — `create_task_with_role`, `update_task_state`, `list_tasks_for_user`
   - `services/user_service.py` — `update_profile`, `apply_privacy_filter`

   Роутеры становятся тонкими: парсинг входа → вызов сервиса → формирование ответа (HTML или JSON).

3. **Тесты на парность.** Добавить в `tests/test_parity.py` сценарии:
   «создание задачи через HTML POST и через `/api/v1/tasks` приводит к одинаковой записи в БД».

## Критерий завершения

- В `routers/` нет ни одного `await db.execute(...)` — только вызовы `services/` или `crud/`.
- Тест `test_parity.py` зелёный.
